# Stage5 proposed contract review

Conditional approval of the design direction; this is not review of the forthcoming implementation or admission evidence. Read existing consumers only; no EOS/tests or source edits.

Keep WaterReference scientific and unchanged. A frozen optional kw-only implementation on WaterCaloricState/WaterState allows the exact existing state types to retain implementation provenance. Default None can preserve positional constructors and ordinary numerical behavior, but changes dataclass fields/asdict and potentially any nested-state canonical schema. Version/document that schema change and prove the specific default provider/target canonical bytes against original fixtures rather than claiming all public bytes unchanged.

Must satisfy before isolated implementation passes review:

1. State consumers must bind implementation as well as reference/method. `water_chemical_potential.py::_liquid` currently checks exact state class, reference is, phase and method only; add state.implementation==water.implementation. `ideal_water_vapor.py::_caloric` needs the corresponding check against its water provider. Otherwise old/new states with identical scientific reference and method can cross the seam invisibly. Alternate response construction must likewise validate returned state implementation, T/P/phase and its descriptor.
2. Source propagation includes `phase_storage.py::LiquidWaterPhase.metadata`, `ideal_water_vapor.py::source_ids`, `rigid_water_gas.py` closure results, `solid_fluid_storage.py:119` and `rigid_fluid_heat.py:228`; all currently use reference.source_ids directly. The latter two are easy omissions. Preserve the default tuple/order exactly; add implementation sources only for alternate providers.
3. `deforming_solid_storage.py::_canonical` has an exact WaterProperties branch; extend only via the explicit helper while keeping its old output unchanged. `solid_reactions.py::_identity`, JoinedWaterVapor.identity and phase-transfer compatibility already carry source_asset_sha256, so a reserved, verified descriptor-digest asset entry can distinguish providers without changing the physical reference. Ensure that entry cannot be overwritten by user assets and always equals the canonical immutable descriptor bytes. Unknown/subclass/duck providers must fail before dataclass fallback accidentally serializes locks/native objects.
4. Descriptor must bind the actual adapter conversion layer and HYBRID dispatch policy, not only the pre-existing stage4 kernel. The public state mapping, offset, response mapping and Python ideal branch change behavior and need source identity. Keep native mass versus public mass/R explicit and include the original source-verified Python ideal/reference dependencies. A caller-supplied descriptor alone is not verification; constructor must verify each identity input and seal resulting fields.
5. Chemical `_model._phi0` and Joined `low._water._model.Fi0` still directly access original Python ideal internals. Providing that verified ideal model explicitly as part of the HYBRID implementation is compatible; do not pretend it is a HEOS derivative facade. Ideal caloric values may remain numerically identical while their enclosing hybrid provenance differs intentionally.
6. `solid_fluid_heat.py` currently hardcodes both transport provider_id and version. Derive truthful alternate metadata; at minimum its version, source IDs and asset digest must unambiguously distinguish the hybrid from Python1.5.5. Scientific method IDs may remain equations-based if implementation identity is separately mandatory; they are insufficient identity alone.
7. Explicit `backend='heos'` must require a verified manifest and fail on unknown selector, missing/invalid manifest or source failure. It must never silently fall back to Python. Exact-class acceptance is a type boundary, not proof of initialization; constructor verification and immutable identity remain necessary. Default loads must not require CoolProp imports/installations. Use lazy imports to avoid a water_properties/helper/new-class cycle.

Suggested bounded verification targets: default canonical fixture equality and explicit schema delta; default/HEOS canonical inequality despite same reference; forged/mismatched state implementation rejection; cross-provider chemical/phase-transfer mismatch rejection; all listed source aggregators and transport identities; unknown/subclass and missing-manifest rejection; PYTHON ideal branch value equality with HYBRID provenance; alternate source/hash/config rejection; one real storage inverse under original gates. Tests and a storage inverse remain Root's work, not evidence provided by this report.

These changes bridge implementation identity and consumers. Prior stage4 point/derivative/printed-value passes do not alone qualify coupled storage or phase-transfer behavior. Process-global reference/config mutation and multi-instance concurrent safety remain outside the proposed admission scope.
