# 下一可执行步骤：来源运行记录接入

本阶段已经有真实 N3 唯一耗尽事件的两条候选和条件性数值接受。
后续从已保存的本次结果开始，不为记录接线再执行不变 EOS。

1. 读取现有 `source_observation_record/schema`、`exact_record` 和运行服务，
   明确哪些 trial、前缀、根、事件、累计账本字段已支持，哪些仍只在研究 JSON。
   复用完整 source capture 编码，避免再次复制其物性字段校验。
2. 为完整来源试算/事件建立显式被动记录入口，关联原输入、每次尝试、完整观测、
   时间与预算、选格、拒绝原因和累计账本。保留不同层级资格与旧失败，未知模式不猜测。
   优先用本次已冻结结果和已有失败输入验证完整读取、缺字段和时间/格关联反例。
3. 研究 JSON 中的 live storage 被省略；新的保存协议应提供可解释的依赖关系，
   不把旧进程的 object id 重新解释成当前共享体积声明。
   被动读取与受控恢复分别交付，源文件/数值配置/模式不足时拒绝 live 恢复。
4. 接 CLI/Python 同一服务及失败导出。随后完成实际 adapter 重建与预算恢复验证，
   再接界面；只有实际执行过的路径才标记支持。

这推进完整 Goal 的运行和溯源要求，不免除重复耗尽、再润湿、完整材料域、
反应/烧结/冷却、公开三机制留出、空间时间收敛、全周期和真实材料多代搜索。
