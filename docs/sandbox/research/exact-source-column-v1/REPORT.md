# 来源固定干质量模型接入既有多格守恒积分器

2026-09-10 UTC，基线 `35225b8`。本增量复用已有 `ConservedState`、`Rates` 与 `integrate_exact`，不是新建一份两格事件求解器。完整 Goal 继续保持 active。

## 实现

`exact_source_column.ExactSourceColumn` 接受实际 `SourceWetColumn` 或其炉程包装。动态摩尔数组严格为每格四列：液水、O2、N2、H2O气体；干固体 kg 质量保持在实际来源 storage 中，绑定进不可变的总能量身份。每格总 U 仍包含 m_dry·积分Cp与液/气储能，没有把 kg 改称 mol 或虚构固体摩尔质量。

`pack/unpack` 检查来源能量身份、完整形状、固定干质量和界面模式；拒绝无身份、外来能量身份与动态机械伸长。改变已确认的干/湿界面模式保持储能定义不变，但会改变算子身份。未来原泥组分质量变化必须用明确混合单位的动态状态及一致反应能量关系，不能继续隐藏在固定参数中。

每次 `evaluate` 仅执行一次实际来源列物理求值，然后将共享 N+1 面液/气摩尔流与面总能量直接交给既有 `Rates`。通用局部 source 槽的四列是 (−phase,0,0,+phase)，这里是液汽相转移，不是新增化学反应。外部 cell power 为零，不再加潜热。`SourceExactEvaluation` 同时保留原逐格反解、液面焓/投影及炉程表面分项，来源细节未因数组化丢失。

接口使用 `ExactEventTime`，程序节点直接复用既有 `ExactProgramView`。新运行采用既有两半步 SSPRK2/Heun 与整步误差比较；原来源列 `integrate_source_column` 是中点法，两种数值方法不要求轨迹逐位相同。此适配不直接准入旧机械专属 `ExactFreeWaterTransfer` 事件驱动器，也未增加完整反解温压联合误差认证。

## 已发现并修复的实际接口问题

独立负例证明：初版 guard 只看化学质量/摩尔源是否为零，会忽略非零 `chemical_reference_power_w` 或 `phase_transfer_included=True`。虽然当前正常 `ReactionDisabled` 始终输出零，该适配拒绝契约不完整。现要求精确 `DisabledChemicalRates`、正确 kg/mol tuple 布局、全部 Fraction 零、参考功率零、相转移标记 False；未把参考功率加入热源。

通用积分器只处理其明确定义的异常，来源模型的其他 ValueError 原本可能越过结构化失败返回。`__call__` 现在保留 `IntegrationError` 和独立的 `DomainExit`，其余 ValueError 转为带原原因链的 IntegrationError；直接 `evaluate` 保留原始诊断。第一次修复错误地假设 DomainExit 是 IntegrationError 子类，被实际负例查出并修复，原失败保留。未知来源错误报告 numerical_failure，明确域外仍报告 domain_exit，两者都保留已有前缀。

## 下一必需事件工作

旧 kg/mol 两格事件路径只按 −phase 计算液库存导数，并将末端残液视为液汽数值校正。来源多格必须按 J_left−J_right−phase 定位净耗尽；即使 phase≤0，液流也可能排空单元。可复用库存二次多项式与共有面根工具，但运输残余的处理需显式成对液体/供体焓转移和独立数值预算，不能借蒸发分数门槛或凭空改为水汽。

同样必须明确事件后干界面的输运/再润湿适用关系。默认关闭未知通道不构成材料规律。本阶段的固定干质量、液气摩尔数组、总U身份和精确时间接口为这条完整路径提供直接入口；没有降低原事件门槛或删去运输耗尽要求。物理路线与复用审查随证据保留。
